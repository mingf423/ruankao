# 大型电商平台架构升级（模拟项目）

> **项目性质：模拟项目。** 本文用于备考中的架构设计训练，不代表个人真实任职经历，不得在论文中冒充真实项目履历。

## 1. 业务背景

假设某中大型电商平台在业务增长过程中遇到订单、库存、商品、支付等模块耦合较高，促销峰值期间响应时间上升，数据库读写压力集中，系统扩容与故障隔离困难等问题。项目目标是逐步演进系统架构，提升可扩展性、可用性、可维护性和可观测性。

## 2. 需求与约束（训练假设）

- 业务需求：支持商品浏览、购物车、下单、库存扣减、支付和订单查询。
- 质量需求：峰值流量可弹性应对；核心交易链路具备故障隔离和恢复能力；订单状态可追踪。
- 数据约束：订单、库存、支付等领域数据需要明确归属；跨服务操作存在一致性要求。
- 技术约束：优先考虑 Java 技术生态；系统需支持渐进式迁移，避免一次性重写。
- 组织约束：服务拆分必须考虑团队维护能力和运维复杂度。

以上均为训练设定，若后续需要量化指标，应标记为假设并给出推导依据，不得伪装成真实项目数据。

## 3. 待解决的架构问题

1. 如何从单体/紧耦合模块逐步划分业务服务边界？
2. 如何治理 API 入口、服务发现、配置、限流、熔断和降级？
3. 如何设计缓存策略并处理缓存一致性、穿透、击穿和雪崩？
4. 如何处理订单、库存和支付之间的分布式事务、幂等、重试与补偿？
5. 如何进行容量规划、弹性伸缩、故障隔离、容灾和可观测性建设？
6. 如何落实身份认证、授权、数据保护、审计和安全开发？

## 4. 架构方案候选

- 分层单体渐进重构：迁移成本相对可控，但独立扩展和团队自治有限。
- SOA/服务化：通过服务契约和集成治理解耦，需关注中心化集成组件和治理成本。
- 微服务：可按业务边界独立部署和扩展，但引入分布式通信、数据一致性和运维复杂度。
- 事件驱动：适合异步解耦和削峰，但需要处理事件顺序、重复、追踪和最终一致性。

最终决策必须结合题目设定的业务规模、团队能力、质量属性优先级和迁移约束，不能预设微服务一定最优。

## 5. 关键架构决策待研究

- 服务边界：商品、订单、库存、支付等领域职责和数据归属。
- 交易一致性：2PC、TCC、Saga、本地消息表、事务消息等方案比较。
- 缓存：缓存粒度、失效策略、热点治理与一致性。
- 消息：可靠投递、幂等消费、重试、死信、顺序和积压治理。
- 可用性：限流、熔断、降级、隔离、故障转移和灾备。
- 安全：身份认证、授权、敏感数据保护、审计和安全边界。
- 可观测性：日志、指标、分布式追踪、告警和故障演练。

|---|---|---|---|
