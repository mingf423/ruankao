> 架构定义、驱动力、4+1 视图和架构描述见[软件架构基础与架构描述](软件架构基础与架构描述.md)。本文只比较风格，不重复视图教程。

## 核心知识框架
分层、客户端/服务器、管道-过滤器、仓库、事件驱动、微内核、面向服务等风格；组件、连接件、约束和架构视图；架构模式与设计模式的层次差异。

## 典型风格比较
| 风格 | 优势 | 局限/风险 | 常见场景 |
|---|---|---|---|
| 分层 | 职责清晰、便于维护 | 跨层调用与性能开销 | 业务层次明确的系统 |
| 事件驱动 | 解耦、异步扩展 | 一致性与追踪复杂 | 异步集成、高吞吐 |
| 微服务 | 独立部署、自治演进 | 分布式复杂度高 | 业务边界与团队成熟 |

## 架构师视角
不能脱离需求宣称某种风格最好，应以质量属性场景、组织能力和技术约束作出权衡。

## 易混点与自测
架构风格/设计模式；组件/连接件；事件驱动/消息队列实现。

## 用一个场景理解风格、构件、连接件和约束

假设线上借阅系统由界面、应用服务、借阅规则和持久化职责组成。若规定请求只能从界面进入应用服务、应用服务调用规则与持久化，底层不能反向依赖上层，这是一种**分层风格约束**。分层不是简单把代码放进四个目录，而是约定允许的依赖方向和层间交互。

| 术语 | 具体场景 | 检查问题 |
|---|---|---|
| 构件 | 应用服务、借阅规则模块、持久化模块 | 是否有稳定职责和接口？ |
| 连接件 | 方法调用、接口调用、消息传递、数据访问 | 同步/异步、失败、超时和数据语义是什么？ |
| 约束 | 规则模块不得依赖 Web 控制器；外部适配不得反向调用业务核心 | 是否明确允许和禁止的关系？ |
| 架构配置 | 当前模块及其依赖关系形成的整体拓扑 | 是否满足风格约束和质量目标？ |

### 风格不是产品，也不是部署形态

- 采用分层风格，不代表必须使用某个 Java 框架。
- 采用事件驱动风格，不代表必须使用某个特定消息中间件；事件也可能由进程内机制传递。
- 采用客户端/服务器风格，不等于已经决定部署几台服务器。
- 采用微服务风格，不只是把单体拆成多个进程；还涉及服务自治、独立部署、数据边界、故障隔离和团队运维能力。

### 同一借阅通知需求的两种候选结构

**同步调用：** 借阅办理直接调用短信适配并等待结果。优点是流程直观、结果立即可见；缺点是短信网关慢或不可用可能拖长主请求，且要明确失败是否影响借阅提交。

**异步事件：** 借阅办理发布“借阅已创建”事件，通知处理者稍后发送短信。优点是主流程与通知执行解耦；代价是需要处理重复投递、失败重试、死信/人工补偿、消息追踪和最终一致性。

题目若只说“对接短信网关”，并没有说明通知是否必须与借阅同步完成，就不能直接判定应采用消息队列。应先询问业务是否允许延迟、失败是否可补发，以及通知失败是否影响借阅结果。

### 风格选择的论证顺序

1. 从质量属性场景和约束确定需要解决的问题。
2. 选出能满足驱动力的候选风格，而不是先选技术产品。
3. 比较收益、代价、风险和团队能力。
4. 将风格约束落实到构件和连接件关系。
5. 用场景验证：该结构是否真的改善目标属性，是否引入新的失败模式。

W01 只建立“风格是一组结构组织和关系约束”的概念；系统化风格比较留到后续周。
