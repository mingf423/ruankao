# UML 建模与设计模式

## 核心知识框架
UML 结构图（类图、组件图、部署图等）；行为图（用例图、时序图、活动图、状态机图等）；架构逻辑、开发、运行和部署视图；常见设计模式的意图、结构、适用条件与代价。

## 架构师视角
模型应服务于沟通、分析、验证和演进；图中明确系统边界、接口、依赖、部署节点和关键约束。

## 易混点与自测
类图/对象图、时序图/活动图、组件图/部署图。

## UML 图如何服务于架构描述

UML 图不是按名字自动归属某一种 4+1 视图；同一种图也可能服务于不同层次的模型。关键看图中表达的元素和它要回答的问题。

| 图/模型 | 常见架构用途 | 借阅系统例子 | 使用边界 |
|---|---|---|---|
| 用例图 | 识别参与者和系统功能边界 | 读者查询、预约，馆员处理例外 | 不能单独说明内部结构和运行时细节 |
| 类图 | 表达领域概念或逻辑关系 | 读者、复本、借阅记录之间的关系 | 详细类图可能属于详细设计，不自动等于逻辑架构 |
| 包图 | 表达开发模块和依赖 | 应用服务依赖规则模块，不允许规则反向依赖 Web 层 | 关注代码组织和依赖方向 |
| 组件图 | 表达组件接口和依赖关系 | 借阅办理组件依赖身份适配接口 | 需说明接口契约，不能只靠方框和箭头 |
| 序列图 | 表达场景中的对象/组件交互顺序 | 创建借阅前先取得身份认证结果 | 适合说明交互，不代替完整进程视图 |
| 活动图 | 表达流程、分支和控制流 | 认证失败分支直接结束创建流程 | 不一定表达部署和组件归属 |
| 部署图 | 表达软件制品到节点的映射 | 应用运行单元访问 MySQL 单实例 | 不能由两个节点方框推断高可用或水平扩展 |

### UML 与 ADL 的关系

UML 是通用建模语言，可通过多种图表达架构的不同方面；ADL（Architecture Description Language）更聚焦架构层次的构件、连接件、配置及其约束，常强调结构的形式化描述和分析能力。两者并非互斥：

- 用 UML 组件图说明模块接口，用部署图说明节点映射，是常见的架构描述做法。
- 当需要描述构件类型、连接件协议、配置合法性或执行自动化架构分析时，ADL 的概念更贴近问题。
- 不要把“UML 能画组件图”推成“UML 就是 ADL”；也不要把“ADL 专注架构”推成“UML 不能表达架构”。

### 识图时先问三个问题

1. 图中的主要元素是职责、代码模块、运行单元还是部署节点？
2. 图要回答谁的关注点？
3. 图中连线是否有明确语义，是否能追溯到架构决策？

例如一张组件图若只展示“借阅办理—身份适配”的依赖，却不说明认证失败时是否允许继续，就还不能证明安全场景已经满足。
