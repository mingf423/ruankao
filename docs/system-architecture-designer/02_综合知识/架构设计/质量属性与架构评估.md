# 质量属性与架构评估

> W01 只要求识别驱动力并写出质量属性场景，配套教学案例见[架构基础与视图](../../03_案例分析/架构基础与视图/README.md)。敏感点、权衡点和 ATAM 仍以本文后续学习为准，不在场景入门案例里展开。

## 核心知识框架
性能、可用性、安全性、可修改性、互操作性、可测试性、可部署性；质量属性场景；质量属性冲突与权衡；敏感点、权衡点、风险；ATAM 等评估方法。

## 质量属性场景模板
| 要素 | 说明 |
|---|---|
| 刺激源 | 谁或什么触发 |
| 刺激 | 发生什么事件 |
| 环境 | 正常、峰值、故障等 |
| 制品 | 系统、组件或接口 |
| 响应 | 系统采取的行为 |
| 响应度量 | 可验证的时间、比例、容量或恢复指标 |

## 案例答题框架
明确目标与优先级 → 场景量化 → 识别架构决策 → 分析敏感点/风险/冲突 → 提出改进与验证指标。

## 场景化理解：质量属性不是形容词清单

质量属性描述系统“做得多好”，不是系统“做什么”。同一功能可能同时受多种质量属性约束。例如“读者创建借阅”是功能；认证失败必须拒绝创建是安全要求；高峰查询 95% 在 2 秒内返回是性能目标。

### 从模糊表达改写为六要素

| 原始表达 | 缺少什么 | 改写方向 |
|---|---|---|
| 系统要快 | 高峰环境、制品、统计口径和响应度量 | 谁在什么时段发起什么请求，哪个功能在何种分位数/比例下满足时延目标 |
| 系统要安全 | 威胁主体、受保护操作和失败响应 | 未认证主体尝试创建借阅，系统拒绝且不得产生借阅记录 |
| 系统要好改 | 变化源、变化内容、影响范围和完成标准 | 规则维护人员调整借阅规则时，不要求修改门禁与短信适配；允许的变更耗时待业务确认 |

六要素中“响应度量”不一定总是数字，但必须可判定。若题干只说“不得创建”，可以把该行为作为明确验收条件；若要求审计、告警或恢复时限却未给数值，应把缺口写成待确认。

### 一个质量属性可能改变多个架构决策

以认证安全为例：认证不仅是登录页面，还影响借阅创建入口、身份适配边界、运行时调用顺序、失败时是否允许继续，以及测试用例。若只在逻辑图上画一个“认证模块”，却没有说明创建动作必须等待认证结果，安全要求就没有落实到运行时行为。

性能目标也不能直接推出缓存。应先确认端到端时延口径、当前基线、并发量、读写比例和瓶颈位置，再决定索引、查询优化、缓存、扩容或其他方案。

### 常见属性冲突与权衡

| 场景 | 冲突关系 | 需要验证的问题 |
|---|---|---|
| 强制调用统一身份 | 安全与性能/可用性 | 外部身份服务超时如何处理？安全约束是否禁止降级放行？ |
| 短信改为异步 | 性能与一致性/可观测性 | 用户是否允许稍后收到通知？如何处理重复、失败和补发？ |
| 服务拆分 | 可修改性/独立部署与可用性/运维复杂度 | 是否真的有独立发布和扩缩需求？团队能否承担分布式故障处理？ |
| 增加缓存 | 性能与数据一致性 | 哪些数据允许陈旧？失效策略和回源压力如何控制？ |

### ATAM 前先把“为什么评估”说清楚

质量属性场景用于描述目标；架构决策影响质量属性；敏感点是某项决策参数变化会显著影响某一质量属性的地方；权衡点则是同一决策影响多个质量属性、形成取舍的地方。ATAM 不是简单给架构打分，而是通过场景、驱动因素和架构决策识别风险、敏感点与权衡点。

W01 只要求能写场景并识别初步冲突；敏感点、权衡点和 ATAM 的系统化步骤在后续学习时展开。不要把“认证可能增加时延”直接断言成已经发生的性能瓶颈。
