# W01｜软件架构基础动手实验

> **用途：** W01 的核心实践底稿。建议用 2.5–3 小时完成，先独立作答，再查看文末参考思路。  
> **材料来源：** 与“架构驱动力与质量属性场景识别”“从需求推导架构视图”两篇原创教学案例共用图书馆线上借阅背景。不是历年真题，也不是实际生产系统。  
> **学习目标：** 把概念变成可检查的架构产物，而不是只会复述定义。

## 实验规则

1. 只使用题干给出的事实。推断必须标为“推断”，未给出的信息标为“待确认”。
2. 每个架构元素都要能追溯到一条需求、质量属性、业务目标或约束。
3. 不以技术名词代替论证。Redis、消息队列、微服务、容器都不是默认答案。
4. 先完成“学员作答区”，再看参考思路。建议把参考答案折叠或暂时移到文档末尾再练习。

## 一、案例材料

某市图书馆计划把柜面借阅扩展为线上预约和到馆自助借还。

| 项目 | 已知材料 |
|---|---|
| 现状 | 单体 Java Web 应用，使用 MySQL 单实例保存借阅数据；借阅规则在应用内既有模块中计算 |
| 用户与功能 | 读者查询并预约可借复本；到馆后自助借出；馆员处理柜面例外 |
| 外部依赖 | 必须对接市统一身份认证、短信网关、RFID 门禁；不得另建读者账号 |
| 项目约束 | 6 人团队，6 个月上线；继续使用既有借阅规则模块 |
| 性能目标 | 周末 9:00–11:00，正常网络下 95% 预约查询请求在 2 秒内返回 |
| 安全要求 | 未通过市统一身份认证不得创建借阅；借阅记录含个人借阅事实，按敏感信息处理 |
| 可修改性要求 | 调整借阅规则时，不应为此改写门禁和短信适配 |

**明确未知：** 当前查询基线、并发量、读写比例、数据库与应用是否同机、规则变更频率、短信同步/异步要求、门禁超时策略、加密与审计细则、预算。

## 七、考试迁移：把实验结果转成答案

### 综合知识

用一句话分别区分：逻辑视图、开发视图、进程视图、物理视图。再解释视点与视图的区别。

### 案例分析

限时 15 分钟回答：
1. 本案例中最重要的三项架构驱动力是什么？
2. 为什么只有部署图不足以描述该系统？
3. 哪两项信息必须标为待确认，不能擅自选择技术？

### 论文素材

用不超过 250 字写一个架构决策段落，必须包含：
- 背景和约束；
- 至少两个备选方向；
- 选择及理由；
- 质量属性影响；
- 尚未验证的风险。

若使用图书馆背景，段落必须注明“模拟案例”，不得写成个人真实项目经历。

## 八、参考思路（完成前请勿阅读）

### 实验 1 参考

- 功能：查询、预约、自助借出、馆员例外处理。
- 质量属性：查询性能目标、未认证不得创建借阅、规则变化不牵动适配。
- 业务目标：6 个月内把柜面借阅扩展到线上。
- 约束/现状：6 人团队、复用既有规则、必须对接三个外部系统、不得自建账号；现状为单体 Java Web 和 MySQL 单实例。
- 待确认：当前查询基线、并发量、同机与否、短信同步/异步、门禁失败补偿、审计要求等。

### 实验 2 参考

性能：读者发起预约查询；环境为周末 9:00–11:00、正常网络；制品为预约查询；系统返回可预约结果；目标为 95% 请求 2 秒内返回。该值是业务目标，不是已测量结果。

安全：未通过市统一身份认证的访问者尝试创建借阅；系统拒绝创建。审计行为和保留期限待确认。

可修改性：规则维护人员在系统上线后调整借阅规则；规则生效，但该变更不要求改写门禁与短信适配。具体变更耗时、回归范围和频率待业务确认。

### 实验 3 参考

边界外：读者、馆员、市统一身份、短信网关、RFID 门禁。边界内：线上借阅系统整体。规则模块、数据库和类属于系统内部。

### 实验 4 参考

逻辑职责可包括预约查询、借阅办理、借阅规则、身份认证适配、通知适配、门禁适配、借阅记录。开发模块可按接入与界面、应用服务、既有规则模块、外部适配、持久化组织。

进程视图至少表达：创建借阅前必须取得认证结果；认证失败停止创建；规则判断在办理流程中完成。门禁失败后的记录一致性策略、短信是否异步均待设计。

物理视图只说明应用运行单元依赖 MySQL 单实例并访问外部系统；应用与数据库是否同机待确认。不要声称已经分机或水平扩展。

### 实验 5 参考

- 逻辑：借阅办理协调认证、规则和门禁职责；预约查询提供复本状态。
- 开发：应用服务编排流程，规则模块保留既有边界，外部适配隔离协议。
- 进程：认证失败即停止创建；门禁失败策略待设计。
- 物理：应用运行单元依赖 MySQL 单实例并访问外部系统，主机关系待确认。

### 自评评分（满分 20）

| 项目 | 分值 | 达标标准 |
|---|---:|---|
| 需求分类 | 4 | 功能、质量、业务目标、约束没有明显混淆 |
| 质量属性场景 | 4 | 六要素齐全，目标与实测区分清楚 |
| 上下文 | 2 | 系统边界正确，外部角色/系统位置正确 |
| 四个视图 | 6 | 每种视图关注点正确，元素能追溯驱动力 |
| 场景追踪 | 2 | 同一场景能跨四视图对应 |
| 证据纪律 | 2 | 未知项未被写成事实，没有无依据技术选型 |

**通过标准：** 16 分及以上，且“证据纪律”不得 0 分。低于 16 分时，不要重读全文；只重做丢分最多的实验，再隔一天闭卷复画。

## 九、概念迁移练习：换一个职责再推导

不要只会复述身份认证这一条链。任选“借阅规则”或“短信通知”，按下表写出它在不同视图中的表达：

| 视图 | 需要描述的内容 | 学员填写 |
|---|---|---|
| 逻辑 | 职责是什么、与谁协作 | |
| 开发 | 代码/模块归属、依赖方向 | |
| 进程 | 运行时何时调用、失败如何影响流程 | |
| 物理 | 运行单元落在哪些节点、依赖哪些外部节点 | |
| 场景 | 哪个端到端过程能检验四种描述一致 | |

再回答：
1. 一个构件是否一定对应一个 Java 类？为什么？
2. 一条连接线至少还需要补充哪些交互语义？
3. 为什么“分层模块”不等于“独立部署服务”？
4. UML 组件图和 ADL 在表达目标上有什么差别？

**参考要点：** 构件是架构职责单元，粒度不等于类；连接件要说明调用/消息/数据语义及超时、失败等关键行为；模块组织不自动决定部署边界；UML 可表达架构侧面，ADL 更聚焦构件、连接件、配置及约束的架构语义。
