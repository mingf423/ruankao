# 架构驱动力与质量属性场景识别（教学案例）

> **题目类型**：原创教学案例，不是历年真题。  
> **适用阶段**：W01。限时建议 40 分钟，先独立作答再对照。  
> **核心考点**：区分功能、质量属性、业务目标和约束；把质量目标写成可检验场景；没有证据就不编造度量。  
> **知识入口**：[软件架构基础与架构描述](../../02_综合知识/架构设计/软件架构基础与架构描述.md)。本案例不要求选择微服务或缓存方案。

## 题目来源与背景

某市图书馆要把现有柜面借阅扩展为线上预约和到馆自助借还。题干给定的材料如下。

- 现状：单体 Java Web 应用，使用 MySQL 单实例保存借阅数据；借阅规则在应用内的既有模块中计算。应用和数据库是否部署在同一台主机，材料没有说明。
- 范围：读者可查询并预约可借复本；到馆后完成自助借出。馆员仍可处理柜面例外。
- 外部系统：必须对接市统一身份认证、短信网关、RFID 门禁。不得另建一套读者账号。
- 复用：6 人团队要在 6 个月内上线，并继续使用现有借阅规则模块，不把规则重写成新的服务。
- 性能目标：周末 9:00–11:00，预约查询在正常网络下 95% 的请求于 2 秒内返回。这是馆方提出的目标，不是已经测量到的结果。
- 安全要求：未通过市统一身份认证的访问不得创建借阅。借阅记录包含个人借阅事实，按敏感信息对待。
- 变更要求：调整借阅规则时，不应为此改写门禁对接和短信对接。

材料没有给出：当前查询实际耗时、读写比例、并发人数、规则一年变更几次、短信必须同步还是可以异步、等保或加密的具体级别、预算金额。

请回答：

1. 列出本系统的架构驱动力，并分成功能需求、质量属性、业务目标、约束。对材料没有证实的内容单独列出。
2. 为性能、安全、可修改性各写一个质量属性场景。材料没给的响应度量不要编造，明确写成待确认。
3. 说明哪些驱动力会互相牵制，以及本周还不应该据此做出的技术结论。

## 考点定位

- 官方大纲范围：软件架构概念、架构需求中的质量场景。ABSD 的完整步骤、ATAM 和架构风格比较不是本题得分点。
- 能力：先把题干事实、假设和待验证信息分开，再写场景。
- 阅卷关注的是分类是否干净、场景是否能检验、有没有把未知说成事实。不奖励提前写出消息队列或微服务。

## 需求与约束识别

### 已知事实

| 类别 | 材料中的表述 |
|---|---|
| 功能 | 预约查询、到馆自助借出、馆员处理例外、沿用既有规则判断 |
| 质量属性 | 周末上午查询的响应目标；未认证不得创建借阅；规则变更不应牵动门禁和短信 |
| 业务目标 | 6 个月内把柜面借阅扩展到线上 |
| 约束 | 6 人团队；必须对接三个指定外部系统；不得自建账号；继续使用现有规则模块 |
| 现状 | 单体 Java Web；MySQL 单实例；规则在应用内 |

### 还不能当作事实

- MySQL 必须永久使用。材料只描述现状。
- 应用已经或必须与数据库分机部署。材料未说明。
- 2 秒目标当前已被违反。材料没有基线测量。
- 短信必须异步，或必须引入消息队列。
- 需要微服务、缓存或读写分离。这些是后续方案，不是驱动力本身。
- 借阅记录的保存期限、加密算法、审计保留天数。

合理假设只允许用于标明缺口，例如“若业务确认规则每月变更，可修改性的度量就要落到变更周期”。假设不能写进“系统已经如此”。

## 参考答案

### 1. 驱动力分类

**功能需求**

- 读者查询可预约复本并创建预约。
- 到馆后由系统按规则完成自助借出，并使用 RFID 门禁。
- 馆员处理柜面例外。
- 借出资格由现有规则模块决定。

这些功能里，对架构更敏感的是“规则判断”和“三个外部系统的职责位置”，不是每个页面的字段。

**质量属性**

- 性能：周末高峰预约查询的响应目标。
- 安全：认证是创建借阅的前置条件；借阅记录敏感。
- 可修改性：规则变化与门禁、短信适配分离。

可用性、可测试性在材料中没有目标，不能写成已经提出的驱动力。

**业务目标**

- 在 6 个月窗口内提供线上预约和自助借还，减少只依赖柜面的限制。

**约束**

- 团队 6 人，窗口 6 个月，限制了能同时重写的范围。
- 身份源必须是市统一身份。
- 规则实现必须复用既有模块。
- 必须与短信网关、RFID 门禁集成。集成方式未限定。

**待确认**

- 性能基线、实际并发、数据库与应用的部署关系。
- 规则变更频率，以及“不改短信和门禁”是否包括短信文案模板。
- 认证失败、门禁超时、短信失败分别应拒绝、重试还是降级。
- 敏感信息的具体保护要求。

### 2. 三个质量属性场景

**性能**

| 要素 | 内容 |
|---|---|
| 刺激源 | 读者 |
| 刺激 | 发起预约查询 |
| 环境 | 周末 9:00–11:00，正常网络 |
| 制品 | 预约查询功能 |
| 响应 | 返回是否可预约的结果 |
| 响应度量 | 95% 的请求在 2 秒内返回。这是目标，不是已测量值 |

**安全**

| 要素 | 内容 |
|---|---|
| 刺激源 | 未通过市统一身份认证的访问者 |
| 刺激 | 尝试创建借阅或预约 |
| 环境 | 系统正常运行 |
| 制品 | 借阅创建入口 |
| 响应 | 拒绝创建 |
| 响应度量 | 材料只要求不得创建。是否记录审计、保留多久，待业务和安全要求确认，此处不补数字 |

**可修改性**

| 要素 | 内容 |
|---|---|
| 刺激源 | 规则维护人员 |
| 刺激 | 调整借期等借阅规则 |
| 环境 | 系统已上线 |
| 制品 | 既有借阅规则模块，以及门禁适配、短信适配 |
| 响应 | 规则生效，且该变更本身不要求修改门禁适配和短信适配 |
| 响应度量 | 材料没有给出从确认到生效的时间上限。答题时应向干系人补问这个上限，不能自行写成“1 天内” |

### 3. 牵制关系与本周不应下的结论

- **上线窗口、团队规模与结构变化的牵制：** 6 人和 6 个月支持“把线上入口、认证适配和门禁适配加到现有规则模块之外”，不支持在没有更多证据时重写全部借阅核心。
- **性能目标与证据的牵制：** 2 秒是验收目标。在没有慢查询、并发和部署事实前，不能认定数据库是瓶颈，也不能认定必须加缓存。
- **安全与易用的牵制：** 统一身份增加一次外部调用，可能影响 2 秒目标。这是后续要测量的权衡，不是现在取消认证的理由。
- **可修改性与复用约束一致：** 规则留在既有模块，门禁和短信放在适配边界，才能满足“改规则不改两端”。这是职责分配，还不是在选消息中间件。

本周明确不要做出的结论：

- 不把单体判断为落后，也不把微服务写成下一步。
- 不规定短信同步或异步。
- 不给出未经材料支持的 TPS、可用性百分比或节省人力数字。

## 五步法映射

1. **业务需求与质量属性：** 线上预约、自助借还；性能、认证安全、规则可修改。
2. **约束与证据：** 团队、周期、三个外部系统、复用规则；性能基线和部署关系缺失。
3. **备选方案：** 本题要求的是识别驱动力，不是方案选型。可接受的比较是“把缺口标成待确认”对比“把缺口填成具体中间件”。前者符合证据规则。
4. **选择：** 先固定驱动力和场景，方案留到有基线之后。
5. **影响：** 认证位置影响安全和延迟；规则与适配分离影响可修改性；团队规模限制同时改动的范围。

## 参考答案得分点

| 得分点 | 答到什么程度 |
|---|---|
| 四类驱动力分开 | 功能、质量属性、业务目标、约束没有互相填空 |
| 事实和未知分开 | 部署关系、短信方式、性能基线被标成未知 |
| 场景完整 | 三个场景都有刺激源、刺激、环境、制品、响应 |
| 度量诚实 | 2 秒按材料引用；审计天数和变更周期不编造 |
| 没有越权选型 | 不把缓存、消息队列或微服务写成本题结论 |
| 指出牵制 | 至少写出窗口与改造范围，或认证与延迟之间的张力 |

建议按上表每项 0–2 分，满分 12。低于 8 分时，把失分写成错题，而不是把参考答案抄一遍。

## 概念拆解：为什么这几句话属于不同类别

本题最容易失分的地方不是不会写六要素，而是把“现状、目标、约束、方案”混成一类。

- “当前是单体 Java Web”描述现状；它不自动意味着必须继续单体，也不自动意味着必须改成微服务。
- “95% 请求在 2 秒内返回”是性能目标；没有监控基线，就不能说当前不达标或已达标。
- “未认证不得创建借阅”是安全行为约束；它必须落实到创建路径，而不只是登录页面。
- “规则变更不应牵动门禁和短信适配”表达可修改性目标；可由职责边界、接口隔离等方式实现，不能直接推导某种框架。
- “6 人、6 个月”是实施约束，会影响方案成本和改造范围，但不是质量属性本身。

### 反例与修正

**反例：** “系统高峰期慢，所以加 Redis；短信对接多，所以加消息队列；单体难维护，所以拆微服务。”

**问题：** 这段话跳过了基线、瓶颈、通知时序、团队能力和拆分边界。它把候选方案伪装成题干结论。

**修正：** 先写清性能目标和待测基线；确认短信是否允许异步；识别规则与外部适配的变更边界；再比较候选方案的收益和代价。

### 自测追问

1. 如果删除“规则变更不牵动适配”这条材料，可修改性是否仍然是明确的本题驱动力？应如何回答？
2. 如果题目只给出“95% 在 2 秒内返回”，还缺哪些信息才能做性能诊断？
3. 为什么“必须使用市统一身份”与“采用某种认证协议”不是同一个层次的陈述？

参考：第一问不能再把该项可修改性要求说成题干明确目标，但仍可把模块边界作为候选设计；第二问至少要补基线、负载、统计口径和瓶颈证据；第三问前者是外部约束，后者是可能的协议/实现选择，需由接口规范决定。
