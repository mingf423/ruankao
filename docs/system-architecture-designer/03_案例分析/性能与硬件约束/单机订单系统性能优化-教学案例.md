# 单机订单系统性能优化（教学案例）

> **题目类型**：原创教学用简化案例，非真实考题原文  
> **适用阶段**：W01 及入门阶段  
> **核心考点**：性能瓶颈诊断、硬件/架构约束、方案比较、质量属性权衡  
> **重要说明**：题干信息有限，参考答案应区分“已知事实”和“待验证假设”，不能把推测写成确定根因。

## 一、题目

某公司现有订单处理系统采用单机部署。随着业务增长，高峰期订单处理出现明显延迟，数据库服务器 CPU 利用率和磁盘 I/O 持续处于高位。公司希望尽量控制成本，提升系统处理能力，并保证高峰期核心下单功能可用。

请回答：

1. 分析当前系统可能存在的性能瓶颈，并说明需要补充哪些诊断信息。
2. 给出两种可行的改进架构思路，比较其适用条件、收益和代价。
3. 推荐优先实施方案，说明实施顺序及其对性能、可用性和数据一致性的影响。

## 二、考点与需求约束

- **业务目标**：提升高峰期订单处理能力，保护核心下单链路。
- **质量属性**：性能、可用性、数据一致性、可维护性。
- **已知约束**：当前单机部署；数据库 CPU 和磁盘 I/O 高位；成本需要控制。
- **未知信息**：应用服务器是否与数据库同机；读写比例；SQL 执行情况；磁盘 IOPS/吞吐；锁等待；连接池使用；数据量和增长率；是否有冗余节点与维护窗口。

答题时先指出未知信息，再提出诊断方案。不要未经证据就把数据库 CPU 高归因为 SQL，也不要把磁盘 I/O 高简单等同于缺少缓存。

## 三、参考范文：诊断、方案与决策

### 1. 性能瓶颈诊断

从题干只能确认数据库 CPU 和磁盘 I/O 在高峰期处于高位，不能直接确认唯一根因。应按以下路径采集证据：

| 观察维度 | 诊断内容 | 可能发现的问题 |
|---|---|---|
| SQL 与执行计划 | 慢 SQL、执行计划、扫描行数、索引命中情况 | 全表扫描、低效关联、索引缺失或失效 |
| 锁与事务 | 锁等待、死锁、事务持续时间、热点行 | 长事务、热点更新、锁竞争 |
| CPU | 数据库进程 CPU、上下文切换、查询复杂度 | 计算密集型查询、排序/聚合开销 |
| 磁盘 I/O | IOPS、吞吐、读写延迟、队列深度、随机/顺序访问 | 随机 I/O 饱和、日志刷盘压力、存储能力不足 |
| 连接与并发 | 连接池活跃/等待数、线程池、请求并发 | 连接池配置不当、线程堆积、过度并发 |
| 业务访问模式 | 读写比例、热点数据、峰值流量、接口分布 | 可缓存读请求过多、热点商品/库存竞争 |

可能的瓶颈包括低效 SQL/索引、事务与锁竞争、数据库计算或存储资源不足、连接池排队，以及单实例缺乏横向扩展能力。必须通过监控、慢日志、执行计划和压测确认根因。

### 2. 两种改进思路比较

| 方案 | 核心做法 | 优点 | 局限与风险 | 适用条件 |
|---|---|---|---|---|
| A：先诊断优化 + 有边界的垂直扩展/缓存 | 优化 SQL、索引、事务和连接池；必要时提升数据库 CPU/内存/存储能力；对商品详情、类目、展示信息等读多写少数据使用缓存 | 变更范围相对可控；可先消除明显低效访问；短期交付风险较低 | 垂直扩展有上限且可能增加成本；缓存带来失效和一致性问题；不解决单点可用性 | 监控证实瓶颈集中在数据库，且短期改造窗口有限 |
| B：应用多实例 + 负载均衡，并按负载特征演进数据层 | 应用服务无状态化、多实例部署、负载均衡；会话外置；数据库按需读写分离、分区或其他扩展；配套限流、熔断、故障切换 | 应用层可水平扩展；降低单实例故障影响；可逐步分散读压力 | 改造与运维复杂度较高；读写分离有复制延迟；数据库写瓶颈仍可能存在；需处理会话、幂等和故障切换 | 应用层 CPU/线程资源也成为瓶颈，或需要提升应用层可用性与扩展能力 |

**方案边界必须说清楚**：
- 应用与数据库物理分离只是部署解耦，不等于应用水平扩展。
- 应用水平扩展需要多个应用实例、负载均衡，并处理无状态化、会话外置、幂等和共享状态。
- 读写分离主要分散读压力，不能直接解决主库写入瓶颈；还要考虑复制延迟、读己之写和故障切换。
- 不能将缓存作为库存一致性的默认解决方案。

### 3. 推荐方案与实施顺序

在题干没有给出更多诊断数据时，推荐采用**先诊断、先消除低效访问，再按证据分阶段扩展**的策略，而不是直接断言某一种架构改造必然有效。

建议顺序：

1. **建立基线**：采集接口延迟分位数、吞吐量、数据库 CPU、I/O 延迟、慢 SQL、锁等待、连接池等待等指标，并进行可重复压测。
2. **先做低风险优化**：根据执行计划优化 SQL 和索引；缩短事务；控制连接池与并发；避免无效查询和重复读。
3. **区分缓存数据类型**：商品详情、类目、图片元数据等展示型数据可按业务一致性要求缓存；库存可用量属于交易关键数据，应以权威库存存储和原子扣减为准。若引入库存缓存，只能作为读优化/展示参考，必须设计预扣减、原子校验、库存回补、幂等和超卖防护，不能让缓存值成为最终扣减依据。
4. **针对剩余瓶颈扩展**：若数据库资源仍饱和，评估垂直扩容、存储升级、读写分离或数据拆分；若应用层也饱和，增加应用实例并通过负载均衡分流。
5. **补齐可用性措施**：关键组件冗余、健康检查、限流、熔断、降级、备份恢复和故障演练；明确单点及恢复目标。

该策略的质量属性影响：
- **性能**：SQL/索引和事务优化减少无效计算与 I/O；合适的展示数据缓存降低数据库读负载；应用多实例可提升应用层并发处理能力。
- **可用性**：多实例、健康检查和故障切换降低单点故障影响；限流和隔离可保护核心下单路径。
- **一致性**：库存扣减以权威数据源的原子操作为准，缓存与读写分离必须显式处理陈旧数据和读己之写。
- **可维护性**：分阶段实施、指标驱动决策可降低一次性大改造风险，但多组件会增加监控和运维负担。

## 四、得分点解读

| 得分点 | 应答体现 |
|---|---|
| 区分事实与假设 | 说明题干仅给出 CPU/I/O 高位，根因仍待诊断 |
| 诊断路径完整 | 覆盖 SQL、索引、执行计划、锁、事务、连接池、I/O 指标 |
| 方案可比较 | 至少两种方案，比较收益、代价、风险和适用条件 |
| 架构概念准确 | 区分部署分离、应用水平扩展、读写分离 |
| 缓存边界清晰 | 展示数据与库存交易数据采用不同策略 |
| 决策有依据 | 先建立基线和优化，再根据剩余瓶颈演进 |
| 质量属性有权衡 | 同时说明性能、可用性、一致性及运维复杂度 |

## 五、五步答题法映射

1. **识别需求**：提高订单处理能力，保障高峰期核心下单可用。
2. **识别约束**：单机部署、数据库 CPU/I/O 高位、成本控制；其他条件尚待补充。
3. **比较备选**：诊断优化与垂直扩展/缓存；应用多实例与数据层演进。
4. **决策理由**：先基线诊断和低风险优化，再按瓶颈证据扩展，避免盲目堆技术。
5. **质量属性**：说明性能收益、可用性提升、一致性风险和运维代价。
